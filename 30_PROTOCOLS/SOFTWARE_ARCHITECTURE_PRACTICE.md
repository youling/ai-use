# 软件架构与工程实践 — Architect Targeted Practice

**Practice Version: 0.1.0** · **Classification: L2 Targeted Reference**

本实践针对多 Agent 长期施工中常见的风险：局部任务已经能跑、文件也分开了，但业务领域、状态归属、变化边界和依赖方向仍纠缠在一起，导致后续扩展必须频繁修改不相关代码。

**目标不是让代码符合某种教科书架构，而是降低下一次真实需求变更的代价。** 技术选型、复用现成能力和 ARCH-0 的外部调研，仍由 [Architect Reconnaissance](../docs/ARCHITECT_RECONNAISSANCE.md) 拥有；图的格式、currentness、stage view 和来源边界由 [Diagram-as-Code](DIAGRAM_AS_CODE.md) 拥有；Work/Review/完成仍按 [Agent Interface](../docs/AGENT_INTERFACE.md) 和项目现行合同执行。本文件只拥有**软件工程分解与架构边界检查的方法**。

## 1. 何时使用

Project/Global Architect 在以下情形按需执行本方法：

- 新增有独立长期语义的业务能力，或修改已有复杂业务工作流；
- 引入、拆分或替换数据来源、数据库、外部服务、模型、GUI/CLI 或网络执行端；
- 实现跨多个子系统/owner 的工作，或出现重复状态、循环依赖、模块职责争议；
- 需要长期多人/多 Agent 接手、代码快速增长，或现有修改波及了明显不相关模块。

**不适用的例子**：单文件 bugfix、无需更改接口或边界的普通小修、已经有 current 架构裁决的窄施工。它们沿用当前项目测试/Review；不为了流程完整而做一次领域重建或新建复杂层次。

## 2. 先按变化与责任拆，再按技术拆

Architect 在需要实质分解时，必须能够回答：

| 问题 | 验证重点 |
| --- | --- |
| 这项能力负责什么、不负责什么？ | 能写出正反两面边界，不能只说“负责业务” |
| 哪些事实由谁拥有？ | canonical 数据、来源观察、派生解释、缓存/展示不能混为一个事实源 |
| 哪些原因会导致它变化？ | 客户端格式/API、税务/业务政策、展示、存储引擎、运行节点的变化是否应相互牵连 |
| 谁依赖谁？为什么？ | 显式入/出接口、依赖方向、调用方可见的契约、允许的失败语义 |
| 什么属于实现细节？ | 外部数据库/SDK/模型/界面/网络协议不应无故泄漏进稳定领域接口 |
| 本次要改哪里？ | owner/write-set、必要的模块触点、变更影响范围、兼容/迁移/回退 |
| 以后要换一个组件会怎样？ | 有界变更实验、依赖图和回归测试，而不是凭文件数量推断解耦 |

判断基础是 **关注点分离（Separation of Concerns）、高内聚低耦合、信息隐藏、显式接口契约和依赖方向**。分解应围绕**领域语义与独立变化的原因**；文件、目录、进程、服务和 Git 仓库只是可选实现边界，彼此不等价。

常见错误信号：

- 为了通过单次测试，把来源解析、客户业务规则、存储访问和 UI 写到同一大模块；
- 把一个大文件改成很多文件，但仍共享全局状态、彼此双向引用或循环导入；
- 为了“清洁架构”机械增加 Repository/Service/Adapter 层，却没有真正隔离变化；
- 让数据库 schema、前端组件或某个 SDK 的专有字段反向决定业务概念；
- 在多个模块复制同一事实的写入权，或把尚未核验的来源观察升级为最终业务结论。

**架构可小，不可含糊。** 一个小型原型可以共进程、共模块甚至先采用简单函数；只需清楚留下哪些接缝未来可能变化，以及当前成本/收益判断。并不默认要求 DDD、六边形、Clean Architecture、微服务或某一种语言。

## 3. 设计与派工：把隐含选择显式化

复杂 Work 的实质实现之前，Architect 应优先从当前 repo/local owners 读出事实，形成最小**边界设计说明**（可直接写在原 Work/ADR/PR，不另建文档数据库）：

1. **领域与责任**：哪些能力/状态属于同一变化原因；每个重要模块的 owner、输入、输出、持久状态及排除范围。
2. **调用与数据流**：画出拥有语义的模块/源/消费者及有类型的依赖边；标出外部系统与不确定边，参见 [Diagram-as-Code](DIAGRAM_AS_CODE.md)。
3. **接口/不变量**：输入输出、标识/时态/错误/幂等/安全边界，以及替换底层时必须保持的外部行为。
4. **实施切片**：先做到可验证的最小纵向切片，限定 Foreman 的 write-set、与其他并行 Work 的冲突面；跨 owner 更改须按现行 authority/contract 路由。
5. **可证伪的检查**：提出至少一个“设计其实没有隔离变化”的反例及其检查方式，例如更换来源适配器却迫使修改业务解释逻辑。

项目原有的设计规范、accepted ADR、兼容性和责任边界高于通用启发式；旧方案有缺陷时由 Architect evidence-backed challenge/修订，Foreman 不得以“工程最佳实践”为名自发扩大 Work。

## 4. 用阶段图反向检查设计

**阶段性绘图不仅是汇报，更是一种外显的架构推理。** 画不清楚 owner、模块责任、来源、边语义或为何变化，通常表明还存在未分辨的设计问题；这属于要调查的信号，不等于只要成功画出图就证明架构正确。

在重要架构决策和阶段性复盘中，Architect 应把以下信息显式映射到图中或其旁边的简短说明：

- 领域/责任边界、谁拥有哪个状态与 canonical source；
- 允许与禁止的依赖方向，以及需要稳定的接口和变化/替换点；
- **本阶段新增、变化或撤销了哪些节点/边**，其中哪些已经由真实代码/测试/Review 支持，哪些仍是候选、UNKNOWN 或 BLOCKED；
- 当前前置依赖、未验证假设、下一 Gate 和下一段实质施工。

若图暴露了循环依赖、双写归属、跨领域直接调用或无法解释的箭头，应回到真实 contract/code/source 检查，必要时修订架构；**不能只是重命名方框或重画布局让图好看**。图的 source/currentness、选图类型和动态增量复用规范由 [Diagram-as-Code §3.1](DIAGRAM_AS_CODE.md#31-阶段性进展图示与领域边界复盘) 唯一定义。

## 5. 让设计质量可以被检验

针对项目实际风险，优先选用成本合理的 **Architecture Fitness Functions（架构适应度检查）**：

| 风险 | 可能的可执行检查 |
| --- | --- |
| 循环依赖 / 禁止跨层访问 | import/dependency graph、AST 静态检查、包边界 lint |
| 接口泄漏底层专有语义 | 接口/Schema contract tests、adapter 替换控制 |
| 重复状态写入权 | canonical writer 的单一归属测试、幂等/冲突负控 |
| 架构修改波及无关领域 | PR 改动路径与允许 write-set 对比、受控替换试验 |
| 外部系统变化破坏核心逻辑 | fake/fixture 适配器、contract/consumer tests |
| 版本升级与恢复失败 | migration/replay/backward-compatibility tests，适用时实机验证 |

没有可行自动化时，可先在精确 PR Review 中说明真实依赖、替换影响和已知缺口；**不因没有架构专用 linter 就自动阻塞所有施工**。相反，已有明确 contract 或当次接受标准要求的检查不能被一张漂亮图替代。

重要结论必须可回到相关的代码、Git diff、测试、Issue、Review 和当前 owner；图是导航与推理工具，`diagram render PASS != architecture semantic PASS`。

## 6. 专业交付的最低证明

针对适用的复杂架构 Work，Architect 的结论能够回答：

- **为什么这样拆，而不是最顺手地直接写？**
- **换一个来源、框架或底层实现，预期真正需要动哪几个边界？**
- **本阶段从哪个可核验状态发展到了哪里？哪条关系还没有证据？**

阶段图示和可核验的 delta 按 Diagram-as-Code 与既有 Durable Trace 写入原 Work/PR/Review；**没有新的审批角色、第二套生命周期或固定层数指标**。真实跨项目边界变化继续由对应 owner/Global Architect 处理，普通细节仍归 Project Architect 自主裁决。
