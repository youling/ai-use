# 第一次使用 ai-use

这是一份**给第一次接触本仓库的人看的上手指南**。它帮助你把 AI 当作可以交接、可核验的项目协作者，而不是只靠聊天记录记住工作的临时助手。

**先分清一件事：** ai-use 主要是一套开放的协作规则、角色合同和模板，**不是安装后自动替你启动多个 Agent 的托管平台**。你可以先只借鉴方法；不必一开始就部署控制面、舰队、Runner 或多模型系统。

> 这页是 Human 的教学入口，不产生执行权限或另一套规范。准备实际执行、恢复、接管任务的 Agent，仍应先按 [Bootstrap](../10_BOOT/BOOTSTRAP_CHECK_PROTOCOL.md) 定位当前治理仓；**第一份规范性文件是该仓当前的 [AGENTS.md](../AGENTS.md)（L0）**。随后按现行任务和场景选择需要的规则，不通读全仓。

## 五分钟体验：一个项目、一件事、一个 AI

先选一个你已有的 GitHub 项目，想好一项**可验证的小任务**。例如“整理一个报错的复现条件、修复范围和验收标准”，不要一开始就让 AI 接管整个公司或所有仓库。

在能访问 GitHub 的 ChatGPT、Codex、OpenCode 或其他 Agent 中复制下面这段，把尖括号中的内容换成你自己的信息：

```text
我想试用 ai-use 的人机协作方式。
工作手册：https://github.com/youling/ai-use
我的项目：<owner>/<project-repo>
本轮目标：<一项具体、可验证的小任务>
本轮授权：只读分析和提出方案，不修改文件、不创建 PR、不执行外部动作。

先定位当前治理仓和项目仓；准备执行角色时，第一份规范性规则读取
当前治理仓的 AGENTS.md（L0），再按任务需要定向读取项目本地规则、
Bootstrap 和 Reading Map，不要通读 ai-use 全仓。

先告诉我：你实际成功读取了哪些资料；当前事实与未知分别是什么；
你建议的任务边界、验收办法、下一步是什么。
没有真实 GitHub 访问能力就明确说明，不要声称已读到实时仓库。
```

收到结果后，你可以先判断 AI 是否真的理解了任务，再**明确授权它执行一个小步骤**。如果你希望结果留存并能由下一位 Agent 接班，在自己的项目仓库中用 Issue 保存任务与验收，以分支/PR 保存代码与文档，用真实检查结果和精确引用记录进展。写入、Review、merge、外部操作依当前权限和任务合同进行，不能靠启动提示词自动授权。

**还没有 GitHub 仓库？** 可以先让 AI 帮你把目标、现状、风险和验收写成一份候选任务说明；有了自己管理的仓库及适当权限后，再采用 durable 工作流。不要把只存在于聊天里的内容称作已完成 GitHub 留档。

## 你想用到什么程度？

| 使用场景 | 推荐起点 | 暂时不用做什么 |
| --- | --- | --- |
| **想了解方法** | 先读本页和 [README](../README.md)，让 AI 解释一种具体协作场景 | 不必安装工具或建立一整套角色 |
| **自己 + 一个 AI 做项目** | 使用上面的最小提示词；在自己的项目 Issue/PR 记录任务、结果、验证与接续点 | 不强制创建 Foreman、控制面或复杂图表 |
| **多个 AI 长期接力施工** | 为项目确定 Architect、Work/Issue、明确的派单和 Foreman 工作范围，使用阶段 checkpoint 与独立 Review | 不允许各 Agent 共享同一可写工作区、靠聊天自称已接班 |
| **搭建完整多仓库协作系统** | 读 [Workspace Bootstrap](../10_BOOT/WORKSPACE_BOOTSTRAP_PROTOCOL.md)，注册自己的 governance 和 control_plane，再按真实需求扩展项目/节点 | 不把维护者的仓库名、私有控制面或设备当成你的部署依赖 |

### 一个最小任务应该怎样留下记录？

先在**你自己的项目仓库**里记录“目标、输入事实、允许修改什么、可验证的完成条件、负责人/下一步”。然后沿当前授权和风险选择简单执行或委派：

```text
Human 给出目标和验收
  -> 项目 Issue / 当前任务指针
  -> Agent 在明确的读写范围内工作
  -> 可复核结果（代码/文档、测试、失败证据）
  -> 分支 / PR / checkpoint / Review（适用时）
  -> 确认结果或留下可恢复的下一步
```

上图是理解顺序，**不是**每件事都要增加五种审批。简单、可逆且范围明确的工作可由有权的 Architect 直接处理；长任务或需要独立执行时才按当前规则委派 Foreman/Subagent。Work、执行尝试、Review 和最终接受并不是同一状态。

## 初次使用时会遇到的几个名字

- **Human**：目标、优先级、重要风险和最终决定的拥有者，也就是你。
- **Project Architect（项目架构师）**：负责项目技术方向、任务边界、协调与结果裁决的 AI 角色；不是仅凭一句“你是架构师”就自动取得写权限。
- **Foreman（工头）**：在已有有效任务派发下，协调一个具体工作及其子任务的 Agent；没有大型任务时不必强制创建。
- **Work / Issue / PR**：分别用于定位工作与派发、保存可恢复的任务事实、审查具体代码或文档变更。一个 GitHub Issue 不天然代表已授权施工。
- **Durable state（持久记录）**：可以被后来者重新找到并核验的仓库/提交/评论/证据。模型自述、聊天记忆或没推送的本地工作区不能冒充远端记录。

## 常见误解

**要先安装软件吗？** 只想借鉴人机协作方法，不需要。仓库也有独立的 [Agent Runtime](../agent-runtime/README.md) 参考实现，但那是可选的工程能力，不能与整套治理方法画等号。

**需要绑定某个模型、AI 平台或维护者的私有仓库吗？** 不需要。提供 GitHub 读写能力的工具各有差异；能否真的读写你的项目，需要实际验证。完整的多仓库部署使用你自己登记的治理仓和控制面，不默认依赖上游维护者的私有系统。

**把链接发给 AI，它就会按规则执行吗？** 不一定。先核验它是否实际读取最新的 `AGENTS.md`、你的项目事实与当前任务；再根据真实工具、授权和验收决定执行。没有访问权限时可以讨论公开或你提供的材料，但不能声称完成了 GitHub 写回、实机测试或部署。

**要把整个仓库喂给每个 Agent 吗？** 不要。第一份规范性读取是当前治理仓的 L0，然后按角色和场景从 [Reading Map](../READING_MAP.md) 选最小必要文档；这样才不会让一次小修复变成全仓治理考试。

**我想给 ai-use 提改进建议怎么办？** 可以在本仓提出 Issue 描述你实际遇到的协作问题与期望结果；修改规则时沿用 [变更生命周期](../30_PROTOCOLS/CHANGE_LIFECYCLE.md) 的 Issue、分支、PR、Review 和可核验交付。先确认现有规则是否已经覆盖，不为同一问题重复建一套规范。
